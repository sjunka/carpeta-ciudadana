De kubectl apply a contenedores corriendo

Todos los componentes hablan solo con el API server: observan cambios (watch) y reaccionan. Nadie llama directo al siguiente paso.

  1. kubectl apply envía el Deployment al API server (autentica, valida).
  2. El API server guarda el estado deseado en etcd. Aún no corre nada.
  3. El controller manager ve el Deployment, crea el ReplicaSet y este crea N pods sin nodo.
  4. El scheduler ve pods sin nodo y asigna cada uno según requests, afinidad y taints.
  5. El kubelet ve un pod asignado a su nodo y pide al runtime que lo arranque.
  6. El runtime descarga la imagen del registry si el nodo no la tiene.
  7. Arrancan los contenedores; el kubelet reporta el estado (Running) al API server.
  8. kube-proxy ve Services y Endpoints y programa la red para repartir tráfico entre los pods.

Flechas dobles = watch sobre el API server + escritura de vuelta. Si un pod muere, el paso 3 se repite solo: loop de reconciliación.
